# ERP & Project Management System

## AI Development Charter — Part 2: Engineering Standards

# DATABASE STANDARDS

Use PostgreSQL as the only relational database.

Use Prisma ORM for all database interactions.

Do not use raw SQL unless there is a proven performance or technical reason.

Always prefer Prisma Client.

Use Prisma Migrations for every schema change.

Never modify the production database manually.

Every model must:

- Have a primary key.
- Have createdAt.
- Have updatedAt.
- Use meaningful names.
- Define proper relations.
- Include indexes where appropriate.

Use UUIDs generated by Prisma whenever suitable.

---

# PRISMA STANDARDS

Always:

- Use Prisma Client.
- Keep the schema clean and organized.
- Define explicit relations.
- Use transactions for multi-step database operations.
- Select only required fields.
- Avoid unnecessary queries.
- Prevent N+1 query problems.

Never expose Prisma errors directly to the client.

Translate database errors into user-friendly API responses.

---

# API DESIGN STANDARDS

Follow RESTful API conventions.

Use plural resource names.

Examples:

GET /users

POST /projects

PUT /tasks/:id

DELETE /companies/:id

Use proper HTTP status codes.

Examples:

200 OK

201 Created

204 No Content

400 Bad Request

401 Unauthorized

403 Forbidden

404 Not Found

409 Conflict

422 Unprocessable Entity

500 Internal Server Error

Never return inconsistent response structures.

---

# RESPONSE FORMAT

Every successful response should follow:

```json
{
  "success": true,
  "message": "",
  "data": {}
}
```

Every failed response should follow:

```json
{
  "success": false,
  "message": "",
  "errors": []
}
```

Keep responses predictable.

---

# VALIDATION STANDARDS

Use Zod for all request validation.

Validate:

- params
- body
- query

Never trust client input.

Validation must happen before Controllers.

Controllers should assume validated data.

Never duplicate validation logic.

---

# AUTHENTICATION STANDARDS

Use JWT.

Implement:

- Access Token
- Refresh Token

Support:

- Register
- Login
- Logout
- Refresh Token

Passwords must always be hashed using bcryptjs.

Never store plain-text passwords.

Never expose password hashes.

---

# AUTHORIZATION

Implement Role-Based Access Control (RBAC).

Permissions should be checked using middleware.

Business logic should never depend on client-provided roles.

Authorization decisions must come from trusted server-side data.

Design the permission system to support future expansion.

---

# SECURITY STANDARDS

Use:

- Helmet
- CORS
- express-rate-limit
- HPP

Store secrets in environment variables.

Never hardcode:

- JWT secrets
- SMTP credentials
- Database URLs
- Cloudinary credentials

Sanitize user input where necessary.

Avoid exposing stack traces in production.

Follow OWASP recommendations whenever applicable.

---

# ERROR HANDLING

Implement centralized error handling.

Create reusable utilities:

- ApiError
- ApiResponse
- asyncHandler
- Global Error Middleware

Avoid repetitive try/catch blocks.

Unexpected errors should be logged.

Expected errors should return meaningful API responses.

---

# LOGGING

Use Morgan for HTTP request logging.

Use Pino for:

- Application events
- Business events
- Warnings
- Errors

Do not use console.log() in production code.

Log enough information for debugging without exposing sensitive data.

---

# FILE UPLOAD STANDARDS

Use Multer for file handling.

Use Cloudinary for persistent storage.

Do not store uploaded files locally in production.

Validate:

- File type
- File size
- Allowed extensions

Reject unsupported files.

---

# EMAIL STANDARDS

Use Nodemailer.

Email logic must live inside dedicated services.

Support templates for:

- Welcome Email
- Password Reset
- OTP
- Invitations

Keep templates separated from business logic.

---

# SWAGGER DOCUMENTATION

Document every endpoint.

Each endpoint should include:

- Summary
- Description
- Parameters
- Request Body
- Responses
- Authentication requirements

Expose documentation at:

/api-docs

Documentation should always stay synchronized with the implementation.

---

# PERFORMANCE STANDARDS

Avoid unnecessary database queries.

Select only required columns.

Use pagination for large datasets.

Avoid loading large collections into memory.

Prepare the architecture for future caching.

Optimize only after identifying bottlenecks.

---

# CACHING STRATEGY

Do not implement caching immediately.

Prepare the architecture to integrate Redis later.

When Redis is introduced:

- Cache frequently accessed data.
- Cache dashboard statistics.
- Cache lookup tables.
- Cache permissions when appropriate.

Always define cache invalidation strategies.

---

# BACKGROUND JOBS

Prepare the architecture for BullMQ.

Background jobs should handle:

- Email sending
- Report generation
- Notifications
- Scheduled maintenance
- Heavy processing

Never block HTTP requests with long-running tasks.

---

# REAL-TIME COMMUNICATION

Prepare the architecture for Socket.IO.

Possible future features:

- Notifications
- Live task updates
- Online users
- Chat
- Activity feeds

Keep real-time logic isolated from business logic.

---

# DOCKER READINESS

The project must be Docker-ready.

Configuration should support:

- Dockerfile
- docker-compose.yml
- Environment variables
- Health checks

Do not couple the application to a specific machine.

---

# TESTING STANDARDS

Prepare for:

- Unit Tests
- Integration Tests

Preferred tools:

- Jest
- Supertest

Write code that is easy to test.

Avoid tightly coupled components.

---

# GIT WORKFLOW

Write meaningful commit messages.

Examples:

feat: implement authentication module

fix: resolve JWT refresh issue

refactor: simplify task service

docs: update API documentation

Keep commits focused on a single purpose.

---

# NAMING CONVENTIONS

Use consistent naming.

Files:

user.controller.js

project.service.js

task.validator.js

Variables:

camelCase

Classes:

PascalCase

Constants:

UPPER_SNAKE_CASE

Database tables:

snake_case

API routes:

kebab-case where appropriate.

Consistency is more important than preference.

---

# CONFIGURATION MANAGEMENT

All configuration belongs inside:

src/config

Every external service must have its own configuration file.

Examples:

database.js

logger.js

mail.js

cloudinary.js

swagger.js

Keep configuration isolated from business logic.

---

# DEPENDENCY MANAGEMENT

Install only packages that are currently needed.

Avoid unnecessary dependencies.

Before introducing any new package:

1. Explain why it is needed.
2. Compare it with alternatives.
3. Explain trade-offs.
4. Wait for my approval.

---

# CODE QUALITY

Write self-explanatory code.

Avoid magic numbers.

Avoid duplicated logic.

Extract reusable utilities when appropriate.

Prefer composition over duplication.

Keep functions focused on a single responsibility.

---

# FINAL ENGINEERING RULES

Always prioritize:

- Maintainability
- Readability
- Scalability
- Security
- Testability
- Performance

Never optimize prematurely.

Never overengineer.

Never sacrifice architecture for convenience.

Whenever uncertain, choose the solution that will be easier for another senior engineer to understand and maintain five years from now.
